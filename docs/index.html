01 —— 定位

会议内容，是最不该上传的那一类文本

云端转写服务解决的是「我不想在本机装模型」。但会议音频里通常同时装着：未公开的排期、客户名单、报价口径、还没宣布的人事决定。 把它上传，换来的是省掉一次 4.86 GiB 的下载。

纪要的做法是把模型搬过来。两个 GGUF 常驻在 ~/Library/Application Support/Minutes/models， 语音识别和纪要生成各跑一个独立进程，只绑定 127.0.0.1。 音频从麦克风到文字，中间只经过两次本机回环请求。

网络

运行期不出网

两个引擎只监听回环地址，应用没有遥测、没有账户校验、没有云 API。除了首次下载权重，跑起来之后不需要任何网络。

成本

没有 key，也没有订阅

不需要注册、不需要额度。代价换了个地方支付：磁盘 4.86 GiB，内存约 4.3 GB footprint，以及首次编译引擎的十几分钟。

可用性

断网也能开会

飞机上、客户内网里、酒店弱网下都一样。识别和纪要生成都在本机 GPU 上跑，不强依赖任何外部服务活着。

代价写在前面

这不是一个「轻量」应用。首次要下 4.86 GiB 权重并逐个校验 SHA256，两个模型同时常驻约 4.3 GB， 而且只在 Apple Silicon 上有意义（arm64 + Metal）。如果你的会议内容不敏感、也不想占这些资源， 用云端服务是更省事的选择——这个项目的价值不在于「本地」这个词，而在于把边界画清楚了。

02 —— 形态

一个窗口，三件事：录、看、读

左边是会议列表，中间是正在进行的实时转写，结束后同一个位置换成纪要。 没有欢迎页、没有引导流程、没有设置向导——打开就是一场会议，或者一份旧纪要。

几个界面决定值得单独说，因为它们都不是「设计偏好」，而是从具体的坑里长出来的：

  • 空状态给一个主按钮，而不是让人去工具栏找。 这里没直接用 ContentUnavailableView 的 actions 形式，因为它在 macOS 14 上有已知的按钮分发崩溃； 手写一个 VStack 加 borderedProminent 按钮就够了。
  • 中间结果用灰字，落定才落墨。 每 1.5 秒刷新一次的文本单独存在 interimText 里，不塞进分段数组。 用户看到的是「这句话还在变」，而不是「这段话被反复改写」。
  • 侧栏的删除按钮常驻占位，只切透明度。 显隐切换会让整行宽度变化、列表跟着跳。按钮一直占 18pt，hover 时才显形，光标移动时列表纹丝不动。
  • 长转写按行懒加载。 整段 Text 会在选中会议时同步排版全文，两三小时的会议足以卡住主线程。 拆成一行一个 LazyVStack 子视图后，只排版可见内容，逐行选择也还在。

还有一处不是性能问题但同样要紧：状态点是会呼吸的。录音时红色 0.9 秒明暗循环，暂停变黄，生成纪要变蓝，失败变橙。 这不是装饰，它回答的是「它现在到底在干什么」——一个每分钟都要被问一次的问题。

03 —— 结构

把最容易崩的东西挪到进程外

一个 SwiftUI 应用，两个由它拉起的原生推理进程。三者之间没有共享内存、没有私有 RPC、没有 Python， 只有 HTTP 和两套公开协议。

运行时契约

进程边界一旦是架构的一等公民，两侧的约定就必须写清楚。下面是实际在跑的约定，不是设计意图的转述：

维度ASR 侧LLM 侧
可执行文件engine/bin/audiocpp_serverengine/bin/llama-server
默认端口8797（避开常被占用的 8787）8788
模型别名minutes-asrminutes-llm
启动参数应用生成 runtime/asr-<port>.json纯命令行参数，无配置文件
数据面multipart/form-data + PCM16 WAVJSON + text/event-stream
身份证明backend=metal + family=qwen3_asr + 已加载build_info 非空 + model_path 一致
超时单请求 600 s，资源 3600 s启动探测 1.5 s，总等待 180 s
为什么不做内嵌

内嵌（把推理当库直接链接）能省掉 HTTP 和进程管理，但会让三件事同时变糟：模型崩了等于应用崩了；权重内存常驻且不可回收； 应用重启必须重新加载几个 GB。当前形态每次识别多一次回环请求（亚毫秒量级），换来崩溃隔离和可以单独重启的引擎。

对「一次会议要跑一两个小时」的场景，这笔交易是划算的。

04 —— 流水线

一条音频的旅程

从麦克风到一份可读纪要，中间八个环节。整条链上没有一处把音频或文本送出本机，只有三处异步：音频回调、识别请求、SSE 流。

节奏参数，都在一个文件顶部

参数值为什么是这个值
pollInterval1.5 s离线识别 25 秒音频约 0.96 秒，这个节奏留了 1.5 倍余量；再密就是空转
minCloseSeconds5 s防止「嗯。」「好。」这类极短句被切成独立段，避免分段碎片化
maxSegmentSeconds15 s连续讲述没有标点时的兜底切分，保证时间戳密度
bufferCapSeconds60 s覆盖引擎崩溃自愈窗口；超出丢最旧，防止内存无界
TranscriptionGate.limit2让「正在进行」与「刚完成」的识别有重叠，又不至于排队雪崩
最短音频0.5 ssamples < 8000 直接返回空文本，不触发模型推理
为什么没有 VAD

代码注释写得很直白：能量阈值在复杂声学环境下不可靠——噪声爬升会漏检，切句点会断词。而这类误判的后果是漏字和断词， 用户自己没法修。

于是断句被从声学搬到了文本：固定 1.5 秒送一次识别，用 ASR 自己给出的句末标点判断能否落段，超过 15 秒再强制切。 最坏情况只是分段粒度不理想，文字本身仍然完整——把不可恢复的错误降级成可恢复的瑕疵，这是整条链上最值得抄的一个决定。

05 —— 并发

三个计数器，换掉三类难查的 bug

并发识别有三个天然会出错的地方：同时压太多请求、慢回来的旧结果覆盖了新文本、完成顺序不等于音频顺序。 三个问题各配一个极小机制，加起来不到 80 行。

闸门 —— 宁可丢，不可堵

TranscriptionGate 是一个 actor 信号量，limit = 2，但提供两种取法，语义完全不同：

  • tryAcquire()：宁可丢，不可堵。1.5 秒节奏的中间结果用它——拿不到名额就跳过这一轮，1.5 秒后还有机会。
  • acquire()：必须拿到。会议结束时冲刷缓冲用它——最后一段音频丢了就永久丢了，值得等。

全用阻塞版，引擎一慢请求就堆积、越堆越慢、最后超时丢一片；全用非阻塞版，收尾那段音频可能永远等不到名额。

代次 —— 迟到结果直接作废

每次送识别前先记下当前代次。切段与冲刷都会让 interimGeneration 加一，结果回来后先比代次，不等就整块丢弃： 

// MeetingSession.pollRecognition — 三道 guard，任何一道不过就安静退出
guard snapshot.generation == interimGeneration, !buffer.isEmpty else { return }
guard isReady(.asr) else { return }
guard await gate.tryAcquire() else { return }

没有这一层，一个慢回来的识别结果会把已经落定的分段又写成中间文本，用户看到的是「刚说过的字退回去」。 这种 bug 不可稳定复现，只能靠机制预防。

排序 —— 完成顺序与音频顺序解耦

落定的时候不假设顺序。每追加一段就按录制时间轴重排、重新编号，晚到的第 5 段不会插到第 4 段前面： 

// MeetingSession.appendSegment — 时间轴是唯一真相，sequence 是它的投影
meeting.segments.append(segment)
meeting.segments.sort {
    $0.start == $1.start ? $0.end < $1.end : $0.start < $1.start
}
for index in meeting.segments.indices { meeting.segments[index].sequence = index }

时间戳来自 Swift 的采集时钟，不依赖模型输出——模型只负责文字，不负责它到底发生在第几秒。

结束是一次事务，不是一串调用

finish() 会被写成一个可等待的事务：重复点「结束」等的是同一个 Task，不会重复识别、重复生成、重复保存。 顺序也固定为先 drain 在飞任务并冲刷缓冲 → 生成纪要 → 保存落盘，任何一步失败都停在 failed 并保留检查点，可以重试。 空会议不能完成，标题生成超时也不能阻塞保存。

06 —— 健康

「就绪」不是布尔值，是一个待证明的身份

端口上有人应答 HTTP 200，不等于「我的模型加载好了」。上一版遗留的 Python worker 也会返回 200，别的 llama.cpp 实例也会。 所以健康检查要证明三件事，任何一件不符就判 incompatible，而不是 ready：

① 运行时

它得是我认识的那个程序

LLM 要求 /props 返回非空 build_info；ASR 要求 health.backend == "metal" 且有版本字段。旧 Python 服务没有这些。

② 路径

它得加载着我要的那个模型

服务自报的模型路径与设置里的期望路径，各自做波浪号展开、标准化、符号链接归一，然后逐字符比对。

③ 加载

它得真的加载完了

LLM 要求 is_sleeping 为假；ASR 要求模型条目 loaded 为真。否则判 starting，继续等。

两条不显眼但必要的卫生

拉起子进程前，代码会从环境里删掉 DYLD_LIBRARY_PATH 和 DYLD_FALLBACK_LIBRARY_PATH。 否则在 Xcode 里启动应用时，继承来的这两个变量会让 llama-server 加载到错误版本的动态库——表现是启动即崩溃，日志里什么也看不出。

启动即退出不重试。 ready 态崩了就退避重试（6 / 12 / 24 / 48 秒封顶），starting 阶段就退出则直接把日志摆出来： 模型路径写错、端口被占、GGUF 与二进制不匹配——这类错误重试一万次也是同样的结果，只会把 CPU 吃满、把真正的原因刷没。

07 —— 供应链

「可复现」得写成脚本，不是写进 README

从 git clone 到「字节级可验证的引擎」，中间隔着一份 19 行的锁文件、两个脚本，和一道 otool 门禁。 上游提交、模型修订、字节数、SHA256 全部收敛到 Engine/dependencies.lock 一处：

锁定项值作用
audio.cpp 提交6f71a3b87105…ASR 服务源码
llama.cpp 提交513ad7ae0770…LLM 服务源码
ASR 权重Qwen3-ASR-1.7B Q8_02,473,017,600 B · SHA256
LLM 权重Qwen3.5-4B Q4_K_M2,740,937,888 B · SHA256

构建脚本的四道门

  1. 工具存在性逐个检查 git cmake clang++ xcrun curl install otool codesign tar 与 metal 编译器。缺任何一个都在第 0 秒失败，而不是编译到一半。
  2. 源码获取三路git fetch --depth 1 优先，失败则下同提交的 tarball，再失败用已验证过的本地归档。每路都留提交印记。
  3. 二进制卫生otool -L 扫产物，出现 Python.framework、Torch、MLX、ffmpeg、/opt/homebrew 就报错退出。「零 Python」不是口号，是门禁。
  4. 原子安装先 install -m 755 到临时名，再 mv 覆盖，最后 ad-hoc codesign。应用运行中升级不会读到半个可执行文件。

下载脚本：把断点续传做对

不用 huggingface-cli，也不用 pip。只有 curl、shasum、stat、xargs，代价是要自己处理分块。 几个细节说明作者确实踩过：

  • 每块用 --range，并校验 HTTP 状态必须是 206——服务器不支持 Range 时会返回 200 和整个文件，不校验就会拼出四倍大小的垃圾。
  • 先写 .download 临时文件，长度正确才 mv；失败的块不会污染已完成的块。
  • 分块文件名零填充序号，cat chunk.* 的展开顺序就是字节顺序，不需要额外排序。
  • 换镜像时保留已完成块，只补缺的那部分。镜像只影响传输，不影响验收：ModelScope → hf-mirror → Hugging Face 依次尝试，无论从哪来，最后都要对上锁文件里的字节数与 SHA256。
08 —— 性能

原生快了多少，以及慢在哪

从 PyTorch/MPS + MLX 换到 audio.cpp + llama.cpp 的 Metal 原生服务，六个指标里五个变好、一个变差。 这张图里没有任何一项被拿掉。

指标旧版原生变化
ASR 11.4 s 音频1.061 s（RTF 0.093）0.545 s（RTF 0.048）−49%
ASR 25 s 音频1.909 s（RTF 0.076）0.957 s（RTF 0.038）−50%
LLM 总耗时2.996 s2.755 s−8%
LLM 生成速度85.30 tok/s80.76 tok/s−5%

ASR RSS约 1.02 GiB约 3.09 GiB+202%
LLM RSS约 3.37 GiB约 3.87 GiB+15%
为什么不能只报一个内存数字

「原生内存降低 51%」和「原生 RSS 上升 202%」两句同时为真。llama.cpp 用 mmap 映射 GGUF，RSS 把映射页也算进去， 看起来更大；phys_footprint 更接近系统实际承压。只引用一半，就是选择性陈述。

量化带来的质量差异也被写下来了：同一个 25 秒样本，旧版开头识别成「数据合在一起…总出力…」，新版是「时聚合在一起…总处理…」。 基准文档的结论是「Q8 不能视为与 FP16 完全等价」，并且明确写了「当前样本没有人工校对参考文本，因此不虚构 CER/WER」。 在一个很容易吹指标的领域，这两句话比任何数字都值钱。

09 —— 边界

它做不到什么

每 1.5 秒一轮，不是逐字浮现

识别是离线轮询：把当前完整缓冲整体送一次，回来替换中间文本。感知是「说完一句，半秒到一秒后上屏」。 要做到真正的逐字流式，得换服务端增量识别——那是另一个协议，不是调个参数。

没有说话人分离，也没有词级时间戳

片段时间戳由 Swift 的采集时钟生成，精度是「段」，不是「词」。要区分谁在说话，需要引入 diarization 模型， 是另一个量级的工程量——现有代码里没有留这个钩子。

上下文 32768、单请求槽

4B 模型上要控内存和首 token 延迟。长会议靠 12000 字符分块的 map-reduce 绕开，而不是靠更大的窗口。 代价是两小时的会议要串行压 N 次，中间能看见「第 2/7 段整理」这样的进度。

首次安装不轻

Xcode 命令行工具、CMake、Git、curl，两个引擎在本机编译（Release + Metal），4.86 GiB 权重下载并逐个校验。 装完之前，它不是一个「双击就能用」的 App——这也是为什么它更适合愿意自己编译的人。

沙箱未启用

应用需要访问任意路径的 GGUF 和本机端口，CODE_SIGN_ENTITLEMENTS 为空。 这既意味着它不可能上架 App Store，也意味着自己编译运行是最合理的使用方式。

10 —— 开始

三步，然后就能开会

# 1. 构建并安装固定提交的 audio.cpp / llama.cpp（Release + Metal）
bash scripts/bootstrap.sh

# 2. 下载固定修订的 GGUF，并验证字节数与 SHA256
bash scripts/download_models.sh

# 3. 打开工程，编译运行
open Minutes.xcodeproj

三个脚本都不要加 sudo。引擎和模型装在当前用户的 ~/Library/Application Support/Minutes， 用 root 跑会去查 root 的目录，结果是应用找不到文件——这条提示同时写在 README 和脚本开头，因为它一定会有人踩。 

~/Library/Application Support/Minutes/
├── engine/bin/                 # audiocpp_server、llama-server
└── models/
    ├── Qwen3-ASR-1.7B-GGUF/qwen3-asr-1.7b-q8_0.gguf
    └── Qwen3.5-4B-GGUF/Qwen3.5-4B-Q4_K_M.gguf

首次运行在系统设置里允许「纪要」使用麦克风。启动后工具栏会实时显示两个模型的状态，语音识别就绪后就能新建会议； 会议结束后双击纪要页标题即可改名并自动保存。

想验证「真的跑通了」

单元测试用的是打桩与纯函数，不碰真实模型。要验证真进程、真模型、真音频，用闭环脚本： 

MINUTES_SMOKE_ASR=/path/to/real_zh_16k.f32 \
MINUTES_SMOKE_LLM=1 \
bash scripts/verify_native.sh

它用 swiftc 把源码编成一个独立可执行文件，不经过 XCTest 宿主——因为环境变量在宿主里常常传不进去， 依赖它的断言会静默跳过，测试显示「全部通过」，实际什么也没验。三道断言都是内容级的：ASR 结果里必须出现「虚拟电厂」， LLM 输出必须同时有 ## 摘要 与 ## 行动项、且不得包含 <think>， map-reduce 必须能从远超 12000 字符的输入里产出非空摘要。

深入一层 架构详解：源码逐行的核对版 → 十三个章节，从进程契约、并发隔离域到供应链门禁与性能基线。每个结论都附文件与行号，可以逐条证伪。
